## 의문 제기

`친절한 SQL 튜닝` 1장 스터디를 진행하는 날이었다. 기본적인 데이터베이스의 구조와 SQL의 처리 과정, 데이터 구조 및 I/O와 관한 내용들이 주를 이루었다. 

스터디는 돌아가며 각자 이해한 내용을 요약하여 설명하는 방식으로 스터디를 진행했고, 스터디원이 1.3.7절 `Table Full Scan vs. Index Range Scan` 에서 다음 내용을 언급했다.

> "Index Range Scan은 Single Block I/O 방식으로만 데이터를 읽을 수 있다" 

책에서는 다음과 같이 설명하고 있었다.
> Full Table Scan은 시퀸셜 액세스와 Multiblock I/O 방식으로 디스크 블록을 읽는다.
> (중략)
> Index Range Scan을 통한 테이블 액세스는 랜덤 액세스와 Single Block I/O 방식으로 디스크 블록을 읽는다

하지만 한가지 의문이 들었다 

1부터 1000까지의 데이터를 삽입할 때, 하나의 블록의 단위가 100이라면, 100씩 10블록이 익스텐트 내에 차례대로 삽입될 것이다.

![익스텐트](/assets/img/posts/2026-09-06-extent.png)

그렇다면 익스텐트 내부는 같은 객체의 데이터끼리만 있기 때문에, 순서가 보장되므로 익스텐트 단위로는 Multiblock I/O가 가능할 것이다.

그럼에도 왜 Index Range Scan은 Single Block I/O를 사용할까?

## 추론 - 이유 예상해보기
Index Range Scan이 Single Block I/O를 사용하는 이유에 대해 먼저 생각해보았다.
Index Range Scan은 시작점부터 끝점 사이에 있는 데이터를 모두 읽는 방식이다. 이 결과가 언제나 유효함을 보장하기 위해서는 데이터가 인덱스 칼럼을 기준으로 정렬되어 있어야 한다. 그러므로 Index Range Scan은 데이터가 반드시 정렬되어 있어야 한다. 

Linked List는 물리적으로는 연속되어 있지 않지만 각 노드를 메모리에 저장하고 해당 메모리 주소를 자료구조를 통해 연결하여 논리적으로 이어져 있는 형식으로 구현된다. 
B-Tree의 Leaf Block 사이의 관계에서도 비슷한 점을 찾을 수 있다. Leaf 노드가 시퀸셜하게 유지하는 것은 논리적으로 그렇게 유지하고 있는 것이고, 실제 ROWID가 가리키고 있는 위치는 디스크의 블록들은 흩어져 있을 것이다.

하지만 내가 제기한 의문대로라면 익스텐트 단위 내에서는 순서가 보장되어 있기 때문에 익스텐트 내부에서는 필요한 범위만큼 잘라서 Multiblock I/O 하면 충분히 읽을 수 있다.
그럼에도 Multiblock I/O를 사용하지 않는 이유는, 무언가가 익스텐트 내의 블록들을 흩어지게 만들어 순서를 보장하지 못하게 되기 때문일 것이다.

그럼 무엇이 블록들을 흩어지게 만든 것일까? 나는 크게 두가지라고 생각했다.

유사한 예시는 메모리 페이징에서 찾아볼 수 있다. 메모리 페이징은 물리 메모리를 일정한 크기로 잘라두고, 메모리가 필요할 때 충분한 메모리 조각을 제공한다. 하지만 물리 메모리는 유한하기 때문에 적절히 디스크로 밀어내고, 필요해지면 다시 적재하는 방식으로 관리된다. 처음 어떤 데이터가 특정 물리적 위치에 배치되었다고 해서, 시간이 지난 뒤에도 그 데이터와 물리적 위치의 관계가 그대로 유지될 것이라고 확신할 수 없다.

데이터베이스도 마찬가지다. 데이터베이스는 읽기 뿐만 아니라 쓰기/삭제 연산도 일어난다. 처음에 데이터가 일정한 순서로 익스텐트에 삽입되었더라도 시간이 지나며 쓰기/삭제 연산이 일어날수록 중간에 빈 공간이 생겼다가, 채워지면서 순서가 뒤섞이게 된다. 따라서 데이터는 일정한 순서를 보장할 수 없으므로 Single Block I/O를 사용한다.

또한, 근본적으로 불가능한 이유가 있다. 삽입 순서의 보장이다. 데이터가 언제나 우리가 기대한 순서대로 들어올 것이라는 보장은 없다. 데이터가 1, 2, ..., 999, 1000 순서로 매번 일정하게 들어오지 않는다. 더불어 인덱스를 어떤 칼럼으로 구성할지 모른다. A 칼럼의 데이터가 순서대로 들어왔다고 하더라도 순서가 보장되지 않은 B 칼럼을 인덱스로 구성한다면 무용지물이다.

## 오류 교정
AI와 함께 내 논리의 오류와 실제 동작에서 맞지 않는 부분을 검증했다. 
요약하자면, 전반적인 방향은 맞으나 논리적 비약이 있고 정립해야할 부분도 있다.

### 1. 오라클의 Heap Table은 정렬하여 저장하는 구조가 아니다.
앞선 추론에서 언급했듯이, 삽입 순서는 정렬된 상태라는 것이 보장되지 않는다. 그냥 우연히 그렇게 삽입되었고, 배치되었을 뿐이다. 테이블 데이터를 정렬한 상태로 저장해야하는 규칙이 없다. 데이터가 들어오는대로 적절한 공간을 찾아서 삽입한다.

따라서 의문의 전제인

> 1부터 1000까지의 데이터를 삽입할 때

자체가 근본적으로 Index Range Scan이 Multiblock I/O로 읽기 어려운 이유를 설명할 수 있는 일반적인 상황이 아니다.

데이터는 순서대로 저장된다고 보장할 수 없다. 또한 Heap Table은 순서대로 저장하는 규칙이 없다

### 2. DML은 근본적인 원인이 아니다.
삽입/삭제 연산이 반복되며 블록에 빈 공간이 생겼다가, 채워졌다가를 반복되면 초기의 순서와 블록 배치가 흐트러질 수 있다는 것은 사실이다. 하지만 그것이 Index Range Scan의 랜덤 액세스가 발생하는 필수 원인도, Single Block I/O의 직접적인 이유도 아니다.

### 2-1. 시간이 지나지 않아도 문제는 발생한다.
DML이 근본적인 원인이 아니라는 것은 이미 알고 있지만, 앞서 언급한 추론의 내용 중 하나이자, 강력한 반례에 대해 설명하고자 한다.
정확한 순서로 데이터가 삽입되고, 삽입/삭제 연산이 발생하지 않는다 하더라도 문제는 발생한다. RDB의 행은 여러 칼럼으로 구성된다. 따라서 정렬 기준 또한 그 칼럼들 중 하나로 선택해서 정렬해야 한다.

`id` 칼럼을 기준으로 순서대로 삽입이 이루어졌다고 가정해보자. `id` 칼럼은 정렬이 된 상태로 예쁘게 저장되어있다. 하지만 어느날 DBA가 `salary` 를 기준으로 인덱스를 생성한다면 어떻게 될까? `salary`는 인덱스에 저장된 키 순서와 ROWID가 가리키는 테이블 블록 순서가 일치한다고 보장할 수 없다.

이처럼 인덱스의 컬럼 구성은 다양하고, 인덱스의 컬럼 구성에 따라 정렬되어야 하는 순서가 완전히 달라진다. 시간은 랜덤 액세스를 심화시키는 한가지 시나리오이지, Index Range Scan이 랜덤 액세스인 근본 이유는 아니다.

## 결론
Multiblock I/O는 물리적으로 연속된 여러 불록을 한번의 I/O Call로 읽는 방식이다. Full Table Scan은 이를 적극 활용할 수 있다. Full Table Scan은 순서가 상관없다. 애초에 전부 읽어버리면 된다.

하지만 Index Range Scan은 효율적으로 소량의 데이터를 읽기 위해서 액세스 조건으로 찾아낸 시작점부터 경계값까지 리프 블록을 연속적으로 읽으며 획득한 ROWID로 테이블 액세스를 한다. 

그러나 다른 보조적인 현상들도 있지만, 근본적인 이유는 Heap Table은 데이터를 정렬 규칙 없이 저장하기 때문에 인덱스 키 순서대로 얻은 ROWID가 가리키는 테이블 블록의 연속성을 보장하지는 않는다.

따라서 Index Range Scan에서 필요한 테이블 블록들이 연속되 있지 않으면, 인접 블록을 묶어서 읽는 순간 필요하지 않은 블록까지 읽게 되므로 Multiblock I/O를 활용하기 어렵다.
